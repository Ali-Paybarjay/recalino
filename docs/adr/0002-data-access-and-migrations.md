# ADR-0002: لایه دسترسی به داده، migration و مالکیت جدول‌ها

## وضعیت

**Accepted** — پذیرفته‌شده توسط مالک محصول در 2026-09-30. ادامه «تصمیم‌های بعدی» [ADR-0001](0001-stack-and-hosting.md).

## تاریخ

2026-09-30

## زمینه

ADR-0001 (Accepted) پایگاه داده را Postgres روی Supabase Free گذاشته و انتخاب لایه دسترسی به داده و migration را به ADR جداگانه سپرده است. الزامات تعیین‌کننده:

- **تراکنش واقعی بین چند ماژول:** ساخت Run، رزرو سهمیه و ثبت Job در یک تراکنش (FR-QUOTA-005، ADR-0001 قاعده ۴)؛ انتشار نتیجه در همان تراکنشی که tombstone جلسه را می‌خواند (FR-ORG-007، PRD-PROC-05).
- **کنترل هم‌زمانی:** قفل ردیف (`FOR UPDATE`) برای رزرو، و `SKIP LOCKED` برای صف (FR-PLT-005).
- **اتصال از Vercel Functions** از طریق connection pooler (Supavisor، حالت transaction).
- **مرورگر هرگز مستقیم به جدول‌ها دسترسی ندارد** (ADR-0001 قاعده ۱)؛ RLS فقط لایه دفاعی دوم است.
- **تغییر ساختار دیتابیس فقط با فایل migration در مخزن** (CLAUDE.md).
- **مرز ماژول‌ها** طبق نقشه قابلیت‌ها یک‌طرفه است و هر ماژول مالک داده خودش است (سند FR، بخش ۳.۱).

## تصمیم پیشنهادی

**Migration با فایل‌های SQL و Supabase CLI؛ کوئری با Kysely روی درایور `pg`؛ یک schema در Postgres برای هر ماژول؛ Supabase JS فقط برای احراز هویت.**

| لایه | انتخاب | دلیل |
|---|---|---|
| Migration | فایل‌های SQL در `supabase/migrations/`، ساخته‌شده با `supabase migration new`. اجرا روی محیط محلی با `supabase db reset` و روی پروژه ابری با `supabase db push` | همان ابزار میزبان؛ RLS، نقش‌ها و تابع‌ها مستقیم به SQL نوشته می‌شوند |
| کوئری | Kysely 0.29 روی `pg` 8 | query builder نوع‌دار بسیار نزدیک به SQL؛ `forUpdate()`، `skipLocked()`، CTE و تراکنش صریح دارد؛ runtime سبک |
| نوع‌ها | تولید خودکار از دیتابیس محلی با `kysely-codegen`، در `packages/core/src/db/types.ts` که commit می‌شود | نوع‌ها همیشه با migrationها هم‌خوان‌اند؛ CI عقب‌ماندن آن‌ها را می‌گیرد |
| تراکنش | یک helper به نام `withTransaction`. تابع‌های عمومی ماژول‌ها `tx` را به‌عنوان ورودی می‌پذیرند، تا تراکنش بین ماژول‌ها بدون دسترسی مستقیم به جدول دیگران ممکن باشد | الزام قاعده ۴ ADR-0001 |
| اتصال در Vercel | Supavisor در حالت transaction (پورت 6543)، pool کوچک برای هر Function، بدون prepared statement نام‌دار | سازگار با اجرای serverless |
| اتصال migration و CLI | اتصال مستقیم یا حالت session | DDL و migration به اتصال پایدار نیاز دارند |
| مالکیت جدول | هر ماژول نقشه قابلیت‌ها یک schema دارد: `acc`، `quota`، `org`، `src` و… . ماژول دیگر فقط از API عمومی TypeScript آن ماژول استفاده می‌کند، نه از جدولش | مرز ماژول در خود دیتابیس دیده می‌شود |
| کلید خارجی بین schemaها | فقط در جهت وابستگی نقشه؛ مثلاً `org.class_session.user_id` ← `acc.app_user` | بدون چرخه، هم‌راستا با قاعده ۳.۱ سند FR |
| دسترسی از بیرون | schemaهای ماژول در Data API در Supabase در معرض نیستند و `public` خالی می‌ماند. RLS روی همه جدول‌ها فعال است و policy ندارد (منع همه) | مرورگر راهی به جدول‌ها ندارد؛ RLS لایه دوم |
| نقش دیتابیس اپ | یک نقش اختصاصی با کمترین دسترسی (مثلاً `recalino_app`)، فقط روی schemaهای ماژول‌ها؛ بدون دسترسی superuser. رمز این نقش در migration نیست و مالک محصول یک بار آن را در پروژه ابری تنظیم می‌کند | اسرار در مخزن نیست؛ خطای کد به کل دیتابیس نمی‌رسد |
| Supabase JS | فقط `@supabase/ssr` برای ورود با Google و نشست؛ نه برای خواندن و نوشتن داده | قاعده ۱ ADR-0001 |

### قواعد همراه

1. migration اعمال‌شده هرگز ویرایش نمی‌شود؛ تغییر بعدی migration تازه است.
2. اعمال migration روی پروژه ابری (`supabase db push`) فقط با تأیید صریح مالک محصول انجام می‌شود، نه خودکار.
3. پس از هر migration، `pnpm db:types` اجرا و نتیجه commit می‌شود. CI اگر نوع‌ها با migrationها نخواند شکست می‌خورد.
4. نام schema یک ماژول فقط داخل پوشه همان ماژول در `packages/core/src/<module>/` می‌آید. یک آزمون ساده مرز این قاعده را بررسی می‌کند.
5. داده seed فقط مصنوعی است (فرض A5).

## گزینه‌های بررسی‌شده

### الف) Supabase JS یا PostgREST برای همه دسترسی‌ها

- **معایب:** تراکنش چندعبارتی فقط با تابع RPC در دیتابیس ممکن است. جدول‌ها از طریق API در معرض می‌مانند و امنیت کاملاً به RLS وابسته می‌شود، که خلاف قاعده ۱ ADR-0001 است.
- **نتیجه:** رد شد؛ فقط برای Auth استفاده می‌شود.

### ب) Drizzle ORM

- **مزایا:** نوع‌دار، سبک و محبوب.
- **معایب:** Schema در TypeScript تعریف می‌شود و `drizzle-kit` migration خودش را می‌سازد. این با migrationهای SQL در Supabase CLI، که RLS و نقش‌ها را هم دارند، دو منبع حقیقت می‌سازد.
- **نتیجه:** رد شد.

### پ) Prisma

- **معایب:** موتور و migration جداگانه، سنگین‌تر در serverless، و محدودیت‌های شناخته‌شده با pooler در حالت transaction.
- **نتیجه:** رد شد.

### ت) SQL خام با `pg` یا `postgres`

- **مزایا:** بدون لایه اضافه.
- **معایب:** بدون نوع‌دهی کوئری؛ خطاهای نام ستون در زمان اجرا پیدا می‌شوند.
- **نتیجه:** رد شد. Kysely همان SQL را با نوع‌دهی می‌دهد و در صورت نیاز SQL خام نوع‌دار را هم می‌پذیرد.

## پیامدها

### مثبت

- تراکنش، قفل ردیف و `SKIP LOCKED` مستقیم و قابل آزمون‌اند.
- مرز ماژول‌ها هم در کد و هم در دیتابیس دیده می‌شود.
- مرورگر هیچ مسیری به جدول‌ها ندارد.

### منفی و کار لازم

- نوشتن migration به دانش SQL نیاز دارد.
- گام تولید نوع پس از هر migration اضافه می‌شود؛ CI آن را کنترل می‌کند.
- **سازگاری pg-boss با تراکنش مشترک** (ثبت Job در همان تراکنش) باید در SPIKE-05 تأیید شود. در غیر این صورت صف با جدول ساده و `SKIP LOCKED` ساخته می‌شود؛ این انتخاب از قبل در ADR-0001 باز گذاشته شده است.
- **کار یک‌باره مالک محصول در پروژه ابری:** تنظیم رمز نقش `recalino_app` و قرار دادن رشته اتصال در متغیرهای محیطی Vercel. راهنمای گام‌به‌گام همراه اولین استقرار داده می‌شود.
