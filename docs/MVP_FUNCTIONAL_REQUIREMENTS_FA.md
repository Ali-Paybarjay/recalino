### ۳.۱. قواعد وابستگی

1. **وابستگی یک‌طرفه است و چرخه ندارد.** هر ماژول فقط از ماژول‌های ستون «وابسته به» استفاده می‌کند. اگر دو ماژول به هم نیاز داشته باشند، باید یکی شوند یا قرارداد بینشان جابه‌جا شود.
2. **کار AI ماژول‌های بالاتر از مسیر PROC اجرا می‌شود.** نمونه‌ها: بازتولید جزوه در NOTE؛ Make similar و Too hard در CARD؛ step تولید کارت پیشنهادی. این کارها از API عمومی PROC ثبت می‌شوند و به‌صورت step ثبت‌شده در موتور PROC اجرا می‌شوند. PROC هیچ ماژول بالاتری را import نمی‌کند؛ رزرو سهمیه و Retry برای همه یکسان است.
3. **واکنش به تغییر، از مسیر رخداد است.** ماژول پایین‌تر رخداد را در همان تراکنش ثبت می‌کند (outbox)، و ماژول بالاتر آن را مصرف می‌کند. نمونه: CARD پس از انتشار NotebookRevision برای کارت‌های وابسته پیشنهاد به‌روزرسانی می‌سازد (PRD-NOTE-04).
4. **هر ماژول مالک tombstone داده خودش است؛ PRIV فقط پاک‌سازی را هماهنگ می‌کند.** PROC پیش از انتشار نتیجه، tombstone جلسه و منبع را در همان تراکنش بررسی می‌کند (PRD-PROC-05، AC-17).
5. **رابط کاربری ماژول جدا نیست.** رفتار هر صفحه در FR ماژولی نوشته می‌شود که مالک آن رفتار است؛ صفحه‌ها فقط ماژول‌ها را کنار هم می‌گذارند.

### ۳.۲. ترتیب ساخت

```text
مرحله ۰  SPIKE-01..05 (پس از پذیرش ADR-0001؛ موازی با FR ماژول‌های مرحله ۱)
مرحله ۱  PLT → ACC → (QUOTA ∥ ORG) → SRC
مرحله ۲  (AIP ∥ LKM) → PROC؛ REC موازی با این زنجیره
مرحله ۳  NOTE → HTML
مرحله ۴  MEDIA → CARD → SRS → (ANKI ∥ PERS)
مرحله ۵  PRIV ∥ OPS ∥ EVAL، به همراه سخت‌سازی سراسری (امنیت، دسترس‌پذیری، Backup)
```

- `∥` یعنی موازی‌پذیر. REC فقط به SRC وابسته است و موازی با زنجیره AI ساخته می‌شود.
- جایگذاری PERS در مرحله ۴ پیشنهاد این سند است؛ PRD بخش ۲۸ آن را صریحاً در مرحله‌ای قرار نداده است.
- اگرچه PRIV در مرحله ۵ است، نسب‌نامه داده (PRD-DATA-05) و tombstoneها از مرحله ۱ طراحی می‌شوند تا حذف کامل بعداً ممکن باشد.
- **مصوب مالک محصول (2026-09-30):** حذف خودکار نسخه موقت صوت (D29) مالکش PRIV می‌ماند، اما همراه PROC در مرحله ۲ تحویل می‌شود. دلیل: نسخه موقت از مرحله ۲ ساخته می‌شود و قاعده D29 نباید حتی موقتاً بی‌اجرا بماند.
- طبق PRD بخش ۲۸، نسخه داخلی می‌تواند بخشی از قابلیت‌ها را نداشته باشد؛ اما **MVP نهایی** کل دامنه بخش ۴ را پوشش می‌دهد.

## ۵. قالب FR

هر FR در فایل ماژول خودش (`docs/fr/<MODULE>.md`) با این ساختار نوشته می‌شود؛ فیلدها همان‌هایی هستند که PRD بخش ۳۱.۱ الزام کرده است.

```markdown
### FR-<MODULE>-NNN — <عنوان کوتاه>

- **ارجاع:** PRD-…، D…، AC-… (در صورت وجود)
- **مبنا:** قطعی (D…) | قاعده پیشنهادی بازبینی | وابسته به دروازه G…
- **اولویت:** P0 | P1
- **مرحله تحویل:** ۰ تا ۵
- **نقش مجاز:** learner | system | operator
- **پیش‌شرط:** …
- **جریان اصلی:** ۱. … ۲. …
- **حالت‌های خالی / بارگذاری / خطا:** …
- **ورودی و اعتبارسنجی:** …
- **تغییر وضعیت:** … (ارجاع به ماشین حالت مربوط)
- **خروجی:** …
- **مجوز دسترسی:** …
- **مصرف / سهمیه:** …
- **Idempotency:** …
- **معیار پذیرش:**
  - Given … When … Then …
```

### ۵.۱. قراردادها

- **شماره‌گذاری:** `NNN` در هر ماژول از `001` شروع می‌شود و پایدار است. FR حذف‌شده با وضعیت «منسوخ» باقی می‌ماند و شماره‌اش دوباره استفاده نمی‌شود.
- **مبنا:** PRD سه نوع اطلاعات دارد (بخش ۱). FRی که از «قاعده پیشنهادی بازبینی» می‌آید، تا تأیید مالک محصول همین برچسب را نگه می‌دارد؛ نمونه‌ها: PRD-REC-03، PRD-SRC-04، PRD-COST-03.
- **اولویت:** همه قابلیت‌های بخش ۴.۱ برای MVP نهایی لازم‌اند؛ اولویت فقط ترتیب داخل هر مرحله را تعیین می‌کند. `P0` یعنی مانع ماژول‌های بعدی یا چرخه محوری D25؛ `P1` یعنی لازم برای MVP نهایی.
- **نقش‌ها:**
  - `learner`: کاربر ۱۸+ احراز هویت‌شده، فقط مالک داده خودش.
  - `system`: Worker و کارهای زمان‌بندی‌شده؛ دسترسی محدود به همان Job.
  - `operator`: پشتیبانی و عملیات داخلی؛ دسترسی استثنایی، محدود، زمان‌دار و حسابرسی‌شده (PRD-PRIV-06).
  - Teacher و سازمان خارج از MVP‌اند (D20).
- **اعداد:** مقدار فنی که PRD تعیین نکرده (سقف طول، اندازه، زمان) یا به قرارداد مربوط (API یا آپلود) ارجاع داده می‌شود، یا با برچسب «پیشنهادی» می‌آید. قیمت و ظرفیت پلن هرگز حدس زده نمی‌شوند (G08).
- **آزمون:** هر معیار پذیرش باید به آزمون خودکار یا دستیِ ثبت‌شده در ACCEPTANCE_TEST_PLAN نگاشت شود. رفتار صف مرور، سهمیه و idempotency با آزمون deterministic سنجیده می‌شود، نه با ارزیابی AI (PRD-SRS-07).

### ۵.۲. نمونه قالب (برای تأیید شکل، نه FR نهایی)

نسخه نهایی این FR در [fr/ORG.md](fr/ORG.md) است.

#### FR-ORG-001 — ایجاد جلسه با New Class

- **ارجاع:** D13، AC-01، PRD-PROC-03
- **مبنا:** قطعی (D13)
- **اولویت:** P0
- **مرحله تحویل:** ۱
- **نقش مجاز:** learner
- **پیش‌شرط:** کاربر وارد شده و اعلام ۱۸+ و Learning Profile فعال دارد (FRهای ACC).
- **جریان اصلی:**
  1. کاربر New Class را انتخاب می‌کند.
  2. عنوان جلسه (اختیاری)، تاریخ جلسه (پیش‌فرض: امروز در timezone کاربر)، دوره (اختیاری) و واحد (اختیاری، فقط وقتی دوره انتخاب شده) را وارد می‌کند.
  3. اگر دوره‌ای انتخاب نشود، جلسه به دوره پیش‌فرض کاربر وصل می‌شود؛ اگر دوره پیش‌فرض وجود نداشته باشد، ساخته می‌شود.
  4. کاربر به صفحه جلسه هدایت می‌شود تا ضبط یا آپلود را شروع کند.
- **حالت‌های خالی / بارگذاری / خطا:** بدون دوره: توضیح «جلسه در دوره پیش‌فرض قرار می‌گیرد». هنگام ارسال: دکمه تأیید غیرفعال است. خطای شبکه: پیام قابل فهم و امکان تلاش دوباره، بدون ساخت جلسه دوم.
- **ورودی و اعتبارسنجی:** سقف طول عنوان طبق قرارداد API؛ نمایش درست متن راست‌به‌چپ؛ دوره و واحد باید متعلق به همین کاربر باشند و واحد باید متعلق به همان دوره باشد.
- **تغییر وضعیت:** ایجاد ClassSession، و در صورت نیاز Course پیش‌فرض. هیچ ProcessingRun یا منبعی ساخته نمی‌شود.
- **خروجی:** شناسه جلسه و هدایت به صفحه آن.
- **مجوز دسترسی:** فقط مالک. ارجاع به دوره یا واحد کاربر دیگر پاسخ «یافت نشد» می‌گیرد و وجود آن را افشا نمی‌کند (PRD-SEC-01).
- **مصرف / سهمیه:** ندارد.
- **Idempotency:** درخواست کلید idempotency دارد؛ ارسال دوباره همان کلید، همان جلسه را برمی‌گرداند (PRD-PROC-03).
- **معیار پذیرش:**
  - Given کاربری بدون هیچ دوره، When New Class را بدون انتخاب دوره تأیید کند، Then یک جلسه در دوره پیش‌فرض ساخته می‌شود و Unit خالی می‌ماند (AC-01).
  - Given کاربری که دوره پیش‌فرض دارد، When جلسه دیگری بدون انتخاب دوره بسازد، Then جلسه به همان دوره پیش‌فرض وصل می‌شود و دوره پیش‌فرض دوم ساخته نمی‌شود.
  - Given یک درخواست ایجاد با کلید idempotency، When همان درخواست دوباره ارسال شود، Then همان جلسه برگردانده می‌شود و تعداد جلسات تغییر نمی‌کند.
  - Given شناسه دوره‌ای متعلق به کاربر دیگر، When در درخواست ایجاد استفاده شود، Then پاسخ «یافت نشد» است و هیچ جلسه‌ای ساخته نمی‌شود.
