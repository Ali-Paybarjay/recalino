# گزارش اجرای آپلود قابل‌ادامه و اعلان نتیجه — 2026-10-08

درخواست مالک محصول و معیارهای پذیرش در [طرح D47](../plans/BACKGROUND_UPLOADS_2026-10-08.md) ثبت شده‌اند. این تغییر روی زیرساخت فعلی Recalino اجرا شده است: Next.js، Vercel Blob خصوصی، Postgres و صف پایدار Job. سرویس پولی تازه یا اپ Native اضافه نشده است.

## رفتار نهایی

- فایل‌های انتخاب‌شده پیش از ارسال، با شناسه‌های پایدار دسته، فایل و ایجاد منبع در IndexedDB حساب ذخیره می‌شوند. پس از تأیید ذخیره، جابه‌جایی بین صفحه‌ها ارسال را قطع نمی‌کند؛ reload فایل و قطعه‌های باقی‌مانده را بازیابی می‌کند.
- فایل‌ها، عکس‌های ضبط‌شده و صوتِ یک پردازش از قبل تأییدشده قابل بازیابی‌اند. انتقال صوتِ قدیمی فقط Run موجود را فعال می‌کند و پردازش پولی جدیدی ایجاد نمی‌کند.
- منبع و رسید دسته در یک transaction متصل می‌شوند. سرور پس از تأیید همهٔ فایل‌های اعلام‌شده، مستقل از پیام پایانی مرورگر دسته را می‌بندد. صوت فقط پس از ذخیرهٔ معتبر اصل روی دستگاه تأیید می‌شود.
- فایل ناموفق قابل تلاش مجدد یا کنارگذاشتن صریح است. فایل ردشده، PDF رمزدار و فایل گمشده مسیر بازیابی دارند. لغو پس از تأیید سرور اصل موقت صف را پاک می‌کند؛ دسته‌ای که پردازشش شروع شده از کنترل لغو دستهٔ ارسال آسیب نمی‌بیند.
- پردازش سرور با checkpoint، lease، retry و Cron موجود ادامه دارد. نتیجهٔ کامل، ناقص یا نیازمند اقدام در inbox حساب ثبت می‌شود و Push اختیاری از صف پایدار ارسال می‌شود.
- حساب‌ها صف جدا دارند. حذف حساب صف فایل، metadata صوت، اصل‌های ضبط و نشانگرهای محلی را پاک می‌کند و نوشتن دیررس نمی‌تواند آن‌ها را دوباره ایجاد کند. خروج، گیرندهٔ Push همین دستگاه را سمت سرور حذف می‌کند.

## بهبود زمان

ارسال مستقیم به Blob حفظ شده است؛ قطعه‌ها تا سه درخواست همزمان ارسال می‌شوند. قطعه‌های تأییدشده و checksumهای آماده‌شده دوباره محاسبه یا منتقل نمی‌شوند. محاسبهٔ hash در Worker انجام می‌شود تا رابط گوشی پاسخ‌گو بماند.

آماده‌ساز PDF تا سه صفحهٔ انتخابیِ بدون cache را از یک بار دریافت و بازکردن اصل فایل آماده می‌کند. آزمون renderer واقعی برای JPEG و JPEG2000 این استفادهٔ مشترک را بررسی می‌کند. هر invocation همچنان فقط یک فراخوان OCR پولی دارد؛ سهمیه، timestamp صوت، پرداخت و checkpointهای موجود حفظ شده‌اند. درصد ثابت افزایش سرعت ادعا نمی‌شود؛ نتیجه به شبکه، اندازهٔ فایل و زمان پاسخ provider وابسته است.

این بخش سابقهٔ بررسی workspace مشترک است. تغییرات هم‌زمان چت دیگر حفظ شده‌اند؛ نتیجهٔ نسخهٔ جداگانهٔ انتشار در بخش زیر ثبت شده است.

آخرین بررسی‌های اضافی شامل ۳۴ آزمون صف و خطاهای verification، ۱۱ آزمون metadata و انتقال صوت دستی، و آزمون service worker با گزینهٔ `silent: true` بودند. تلاش مجدد صوت دستی برای گرفتن lease کلاس منتظر می‌ماند؛ اقدام‌های صریح صف فایل در صورت نگرفتن lease، پیام اقدام در تب دیگر را نشان می‌دهند. انتقال دوره‌ای می‌تواند بدون تغییر checkpoint منتظر آزادشدن lease بماند.

### اصلاح خطای آشکارشده در CI

commit نخست `1d9676b9f880491f5e95fe4bc9133461bb80b1fd` push شد و build ابری آن آماده بود. هفت بررسی deployment محافظت‌شده موفق شدند و لاگ‌های بازهٔ بررسی صفر runtime error و صفر 5xx داشتند. این build به دامنهٔ اصلی منتقل نشد: دو اجرای CI هر دو هنگام `afterAll` آزمون موجود `reviewQueue.int.test.ts` در بستن pool دیتابیس timeout شدند، در حالی که assertionهای مالکیت همان آزمون موفق بودند.

علت، بازگشت زودهنگام خطای یکی از readهای `getReviewQueue` با `Promise.all` بود؛ readهای موازیِ صف‌شده می‌توانستند پس از خروج handler هنوز فعال باشند. اصلاح در دو فایل اضافیِ محدود به مرور، منتظر پایان همهٔ readهای شروع‌شده می‌ماند و سپس همان خطا را برمی‌گرداند. ترتیب و سهمیهٔ مرور و نتیجهٔ کنترل مالکیت تغییر نکرده‌اند؛ timeout یا assertion موجود ضعیف نشده است.

regression با readهای کنترل‌شده پیش از اصلاح شکست خورد و پس از اصلاح پاس شد. دو فایل integration هدفمند با هر شش آزمون موفق شدند. دروازهٔ کامل `pnpm verify` نسخهٔ اصلاح‌شده نیز موفق شد: ۲۵۹۴ آزمون در ۲۵۹ فایل پاس شدند، یک آزمون/فایل موجود skipped بود و اجرا ۷۵۵٫۳۳ ثانیه طول کشید. lint، همهٔ typecheckها و مرزهای ۱۰۲۲ ماژول / ۴۴۰۶ وابستگی موفق بودند. ساخت production تازه و بررسی secretهای bundle هم موفق شدند.

نسخهٔ اصلاح‌شده از commit نهایی در CI بررسی و برای Production دوباره build می‌شود؛ build قبلی به‌عنوان نتیجهٔ نسخهٔ نهایی معرفی نمی‌شود. دامنهٔ تجمعی انتشار اکنون همان ۹۵ فایل قابلیت، به‌اضافهٔ اصلاح محدود `srs/review.ts` و regression آن است.

### هماهنگی آزمون‌های قدیمی صوت با صف سراسری

مرحلهٔ کامل verification در CI commit `ac821d92b843c316ab9f8d94de4ac4c173707995` موفق شد. اجرای محلی گستردهٔ مرورگر، ۱۱ سناریوی جدید را دوباره پاس کرد و چهار انتظار قدیمی صوت را آشکار کرد: ترتیب قطعه‌ها سری فرض شده بود، پیام‌ها و دکمهٔ بازیابی از صفحهٔ قبلی خوانده می‌شدند و fixture فقط فهرست Runهای صفحه را mock می‌کرد، در حالی که مدیر سراسری از مسیر مستقل Run و activation استفاده می‌کند.

fixture اکنون snapshot و GET/activation همان Run را شبیه‌سازی می‌کند. آزمون‌ها تعداد دقیق ارسال هر قطعه، ترتیب leaseهای تازهٔ قطعهٔ retry، همهٔ receiptها و تکمیل/activation یکتا را حفظ می‌کنند؛ ترتیب بین قطعه‌های مستقل مجاز به همزمانی است. خطای integrity از وضعیت صف سراسری خوانده می‌شود و تکمیل/activation همچنان ممنوع می‌ماند. gateway آزمون قطع‌شده تا اقدام بازیابی unavailable می‌ماند؛ قطعه‌های تأییدشده بعد از reconnect یا بازگشت دوباره فرستاده نمی‌شوند. هر چهار سناریوی اصلاح‌شده در ۵۹ ثانیه موفق شدند. این هماهنگی، کد production را تغییر نمی‌دهد.

### بررسی SSR و رگرسیون‌های کامل مرورگر

بررسی با `next start` و همان deadlineهای CI نشان داد انتخاب فایل و تغییر تاریخ می‌توانست پیش از hydration رخ دهد و event انتخاب از دست برود. کنترل‌های مربوط در `SourcesView` و `DateInput` تا آماده‌شدن handlerها غیرفعال‌اند. پس از این اصلاح، هر ۱۸ سناریوی هدفمند آپلود، صوت، بازیابی و تاریخ کلاس در ۱٫۱ دقیقه موفق شدند. fixture صوت برای شروع انتقال واقعی منتظر event مشاهده‌شدهٔ تکمیل یا خطا می‌ماند؛ assertionهای تعداد دقیق ارسال و تکمیل یکتا حفظ می‌شوند و timeout عمومی افزایش نیافته است.

اجرای نخست هر ۲۰۳ سناریوی production، ۱۹۰ موفق و ۱۳ ناموفق داشت. انتظارهای قدیمی مراحل پنج‌گانهٔ setup، دکمهٔ پایان، دسترسی به لینک در منوی بستهٔ Course tools و متن حذف device با رفتار فعلی هماهنگ شدند. حالت نبود موتور صوت از API واقعی محلی بررسی می‌شود؛ سناریوهای مستقل setup صوت، موتور موجود را mock می‌کنند. assertionهای نبود consent، درخواست میکروفون و voice write خودکار، حذف فقط حساب جاری، نگه‌داشتن bytes تا تأیید حذف و انتقال یادداشت‌های ویرایش‌شده بین دوره‌ها حفظ شده‌اند. URL فایل محلی همچنان باید `blob:` و متعلق به origin سرور آزمون باشد؛ شمارهٔ پورت ثابت از این assertion حذف شد.

نتایج دروازهٔ نهایی، CI و انتشار عمومی پس از پایان اجرا در artifact عملیاتی ثبت می‌شوند. اجرای محلی production از داده‌های مصنوعی loopback استفاده می‌کند؛ `RECALINO_DEV_UI` فقط برای build آزمون محلی/CI فعال است و به Production اضافه نشده است.

بازاجرای کامل مرورگر ۲۰۲ سناریو را در ۶٫۵ دقیقه پاس کرد. تنها شکست جدید، ورود متن تست مدیریت پیام پیش از بازیابی پیش‌نویس بود؛ این تست اکنون منتظر نشانهٔ واقعی autosave حساب مصنوعی می‌ماند. بازاجرای هدفمند همان سناریو موفق شد. بنابراین همهٔ ۲۰۳ سناریو پوشش موفق محلی دارند، اما موفقیت ۲۰۳ سناریو در یک اجرای واحد از نتیجهٔ محلی استنباط نمی‌شود؛ CI نهایی مجموعه را از commit نهایی یکجا اجرا می‌کند.

دروازهٔ نهایی نخست، ۲۵۹۳ آزمون موفق و یک شکست در fixture قدیمی IP rate limit داشت: انتخاب IP از تنها ۲۰۰ نشانی می‌توانست bucket مصرف‌شدهٔ اجرای پیشین را در پنجرهٔ ۶۰۰ ثانیه‌ای دوباره انتخاب کند. هر اجرای همان آزمون اکنون یک کلید مصنوعی مستقل دارد، ولی هر دو درخواست کلید و IP canonical یکسان دارند. انتظار دقیق `[200, 429]` و نبود IP خام در bucket حفظ شده‌اند؛ هیچ تنظیم production یا ظرفیت rate limit تغییر نکرده است. هر شش آزمون فایل در دو اجرای پیاپی موفق شدند؛ دروازهٔ کامل پس از این اصلاح دوباره اجرا می‌شود.

دروازهٔ کامل نهایی پس از این اصلاح موفق شد: `pnpm verify` با Node 24، lint هر ۹۳۹ فایل، تمام typecheckها، مرزهای ۱۰۲۲ ماژول / ۴۴۰۶ وابستگی و ۲۵۹۴ آزمون موفق در ۲۵۹ فایل؛ یک آزمون/فایل موجود skipped بود. مدت تست‌ها ۷۱۸٫۹۸ ثانیه بود. dry run نهایی Vercel، ۱۱۰۰ فایل / ۷۴۶۰۶۲۲ بایت و صفر مسیر حساس یا artifact محلی در بستهٔ ارسال گزارش کرد.
