# اعلان آماده‌شدن فایل و نتیجهٔ پردازش

این بخش به درخواست صریح مالک محصول در 2026-10-08 اضافه شده است. متن انگلیسی مرکز اعلان، وضعیت Push و اقدام خروج در `ui/notifications/copy.ts` ثبت شده و از Button، Sheet، آیکون‌های موجود و tokenهای رابط استفاده می‌کند.

Run نهاییِ جاری کلاس یک اعلان حساب‌محور در `plt.notification` ثبت می‌کند: نتیجهٔ کامل، نتیجهٔ ناقص یا نیازمند اقدام. Run قدیمی که پردازش جدیدتری جای آن را گرفته، رسید ثبت می‌کند و اعلان تازه‌ای نمی‌فرستد. کلید یکتا برای خروجی موفق بر پایهٔ شناسهٔ نسخهٔ خروجی و برای شکست بر پایهٔ Run است. ثبت نشانگر `proc.processing_run.notification_recorded_at`، inbox، snapshot گیرندگان و Job ارسال در یک transaction انجام می‌شود. Cron هر دقیقه completion ازدست‌رفته را بازیابی می‌کند و پیش از اعلان، انتشار خودکار جزوه و کارت را تکمیل می‌کند. بازیابی به‌صورت پیش‌فرض حداکثر ۲۵ Run دارد و پس از هشت ثانیه Run دیگری را شروع نمی‌کند؛ باقی‌مانده در نوبت بعد ادامه می‌یابد. شکست یک Run مانع رسیدگی به نتیجه‌های بعدی نمی‌شود. پردازش و اعلان به بازبودن صفحه وابسته نیستند.

Push فقط با کلیک کاربر و مجوز مرورگر فعال می‌شود. `sw.js` فقط اعلان را نمایش می‌دهد و لینک داخلی نتیجه را باز می‌کند؛ صفحه یا API خصوصی را cache نمی‌کند. همهٔ اعلان‌های پردازش با `silent: true` مطابق [استاندارد Notifications API](https://notifications.spec.whatwg.org/#dom-notificationoptions-silent) درخواست می‌شوند تا صدا و لرزش ایجاد نکنند؛ پشتیبانی و رفتار نهایی همچنان به مرورگر و سیستم‌عامل وابسته است و سکوت روی همهٔ دستگاه‌ها تضمین‌پذیر نیست. عنوان کلاس و محتوای فایل در متن روی lock screen نمی‌آیند. inbox پس از خروج از صفحه پایدار می‌ماند و اعلان داخل برنامه در فازهای فعال ضبط تا Stop نمایش داده نمی‌شود.

ارسال از صف فعلی `plt.job` با حداکثر ۱۲ تلاش، backoff و timeout ده‌ثانیه‌ای استفاده می‌کند. checkpoint جداگانهٔ هر دستگاه از ارسال مجدد به دستگاه موفق جلوگیری می‌کند؛ پاسخ‌های 404/410 اشتراک منقضی را حذف می‌کنند. اختلال پس از تحویل شبکه و پیش از checkpoint ممکن است به تکرار برسد؛ tag ثابت اعلان و topic ثابت Push آن را در دستگاه جایگزین می‌کنند. حذف حساب یا کلاس فوراً اعلان‌ها را پاک می‌کند و حذف حساب گیرندگان Push را نیز می‌زداید. خروج از حساب گیرندهٔ همین دستگاه را سمت سرور حذف می‌کند؛ unsubscribe مرورگر best-effort است.

## پیکربندی و اجرای محلی

```powershell
node tools/web-push/configure-local.mjs
pnpm exec supabase migration up --local
pnpm db:types
pnpm dev
```

اسکریپت فقط `.env.local` ریشه و `apps/web/.env.local` را تکمیل می‌کند، کلید موجود را حفظ می‌کند و هیچ کلیدی چاپ نمی‌کند. سه متغیر لازم: `RECALINO_WEB_PUSH_PUBLIC_KEY`، `RECALINO_WEB_PUSH_PRIVATE_KEY` و `RECALINO_WEB_PUSH_SUBJECT`. کلید خصوصی فقط سمت سرور است. در production باید subject یک نشانی تماس HTTPS یا mailto واقعی باشد و همان جفت کلید در همهٔ اجرای سرور ثابت بماند؛ تولید مجدد کلید، اشتراک‌های موجود را نامعتبر می‌کند. مالک در ادامه، push و deploy را صریحاً مجاز کرد. migrationها و سه متغیر sensitive فقط در پروژهٔ production مجاز تنظیم شدند؛ نتیجهٔ بررسی‌ها و انتشار در گزارش background-uploads-verification و artifact عملیاتی ثبت می‌شود. تست‌ها هیچ Push واقعی به کاربران ارسال نمی‌کنند.

در iOS/iPadOS، Push برای وب‌اپ افزوده‌شده به Home Screen و با مجوز کاربر قابل استفاده است؛ مرورگر فاقد Push همچنان inbox دارد. این شرط و لزوم اقدام مستقیم کاربر در [راهنمای رسمی Apple](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) آمده است. Push به سیاست و تنظیمات سیستم‌عامل، اتصال و اجازهٔ اعلان وابسته است؛ inbox منبع پایدار نتیجه است. آپلود ناتمام روی گوشی بسته‌شده ادامهٔ تضمین‌شده ندارد و با بازگشت از قطعهٔ باقی‌مانده از سر گرفته می‌شود.

## بررسی‌ها

تست‌های endpoint از SSRF جلوگیری می‌کنند. آزمون‌های integration مالکیت حساب، deduplication، snapshot گیرندگان، retry هر دستگاه، حذف گیرندهٔ منقضی، completion ازدست‌رفته و خروج امن از حساب را می‌سنجند. آزمون service worker نتیجه را با صفحهٔ بسته و navigation محدود به مسیر داخلی بررسی می‌کند؛ هیچ Push واقعی در آزمون‌ها ارسال نمی‌شود.
