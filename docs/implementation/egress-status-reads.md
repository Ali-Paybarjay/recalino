# کاهش انتقال داده در وضعیت پردازش

تاریخ: 2026-10-14

## علت

`getRun`، `listRuns` و بازیابی acknowledgement برای برگرداندن وضعیت پردازش، کل
ردیف `processing_run` را از دیتابیس می‌خواندند. snapshot ورودی شامل متن استخراج‌شده
است و تنظیمات تأمین‌کننده نیز در پاسخ وضعیت مصرف نمی‌شوند. فقط حذف این داده‌ها در
پاسخ API کافی نیست؛ پیش از آن، انتقال از Supabase به سرور برنامه انجام شده است.

در snapshot آمار دیتابیس ابری، پرس‌وجوی فهرست پردازش 38,264 بار اجرا شده و 139,832
ردیف برگردانده است. این آمار از آخرین reset تجمعی است و آمار یک دوره صورتحساب نیست.

## اصلاح

- مسیرهای وضعیت فقط ستون‌های مصرف‌شده را انتخاب می‌کنند.
- PostgreSQL بخش‌های حجیم `units` و `blocks` را از projection ورودی پردازش کلاس
  حذف می‌کند؛ metadata انتخاب برای محاسبه همان selection fingerprint باقی می‌ماند.
  این تغییر روی داده ذخیره‌شده اعمال نمی‌شود. snapshot پردازش auxiliary در وضعیت
  استفاده نمی‌شود و همراه وضعیت دریافت نمی‌شود.
- خواندن snapshot کامل برای ادامه آپلود و اجرای واقعی پردازش همچنان برقرار است.
- `hasPublishedNotebook` از ماژول NOTE فقط اتصال revision جاری به نسخه دانش زنده و
  متعلق به همان کاربر/جلسه را بررسی می‌کند. polling آمادگی جزوه، متن مدل یا ویرایش‌ها
  را بارگیری نمی‌کند. خواندن جزوه در صفحه مطالعه همچنان از `getNotebook` استفاده می‌کند.
- `getRun` ردیف را فقط با شناسه می‌خواند و مالکیت را با `assertOwner` بررسی می‌کند؛ مانند
  `ownedRun`، شناسه run کاربر دیگر همچنان پشت همان 404 سیگنال `ownership_denied` را به
  `recordSecurityEvent` می‌رساند (FR-PLT-002). فیلتر `user_id` در SQL این سیگنال را حذف می‌کرد.
- پرچم `regeneration` در estimate و کمبود سهمیه، وجود نسخه دانش زنده را با
  `listAvailableKnowledgeReferences` (فقط شناسه و شماره نسخه) می‌سنجد، نه با `getLatestVersion`
  که مدل کامل را می‌خواند.
- مرورگر: `SourcesView` و `ProcessingView` فقط وقتی صفحه دیده می‌شود و آنلاین است تازه
  می‌شوند؛ `SourcesView` با بازگشت به صفحه یا شبکه یک بار تازه می‌شود. PDF رمزدار منتظر
  کاربر است، پس فقط تا 60 ثانیه پس از تلاش unlock با timer تازه می‌شود؛ نتیجه unlock در
  `after()` نوشته می‌شود و وضعیتی برای انتظار ندارد. loop یادگیری و شروع آپلود (D29، D60)
  تغییر نکرده‌اند.

## تغییر رفتار ثبت‌شده

- snapshot قدیمی کلاس که `units` یا `blocks` آن با schema فعلی parse نمی‌شود، اکنون
  selection fingerprint می‌گیرد؛ پیش از این بدون fingerprint به مقایسه `sourcesVersion`
  برمی‌گشت. fingerprint به `units` و `blocks` وابسته نیست، پس مقدار تازه درست است.
- `hasPublishedNotebook` برای نسخه دانش tombstone‌شده یا ناهمخوان `false` برمی‌گرداند؛
  `getNotebook` در این حالت خطا می‌داد و کل خواندن وضعیت شکست می‌خورد.

اندازه‌گیری فقط‌خواندنی روی 61 ردیف فعلی دیتابیس، اندازه JSON ستون‌های کامل را
15,600,418 بایت و projection وضعیت را 99,078 بایت نشان داد. برای 32 ردیف پردازش کلاس
به تنهایی، اندازه از 6,513,545 به 87,090 بایت رسید. این اندازه‌گیری شامل فشرده‌سازی
یا سربار انتقال نیست و کاهش کل مصرف ماهانه را تضمین نمی‌کند.

## اعتبارسنجی و محدودیت

35 آزمون مرتبط، بررسی نوع‌ها و مرز ماژول‌ها اجرا شدند. آزمون‌های جدید از کامپایلر
واقعی Kysely با پاسخ دیتابیس مصنوعی استفاده می‌کنند؛ expression اندازه‌گیری نیز با
SELECT واقعی PostgreSQL بررسی شد. ساخت کامل روی clone تازه با خطای
`native_audio_binary_missing` در guard پیش از build متوقف شد. Docker محلی در حال اجرا
نبود؛ مجموعه integration و آزمون مرورگر Recalino روی دیتابیس محلی اجرا نشده‌اند.

این اصلاحیه بدون migration است؛ هیچ داده، سهمیه، پلن یا تنظیم ابری تغییر نکرده است.
پس از ادغام و استقرار، Usage به تفکیک پروژه و Shared Pooler بررسی شود.
