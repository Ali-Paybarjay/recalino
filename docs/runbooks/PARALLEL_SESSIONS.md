این روال برای همه نشست‌های Claude Code در این مخزن است. قواعد CLAUDE.md و مرزهای Always / Ask first / Never در PROJECT_SPEC همچنان برای هر نشست برقرارند. این روال آن‌ها را عوض نمی‌کند.

## نقش‌ها

| نقش | کار | کاری که نمی‌کند |
|---|---|---|
| **مالک محصول** | prompt هر task را در نشست تازه می‌گذارد و نام نشست را تنظیم می‌کند. گزارش پایانی را به نشست مدیر می‌دهد. تصمیم‌ها و تأییدها با اوست. دستورهایی را اجرا می‌کند که برای نشست‌ها مسدودند، مثل `vercel deploy --prod`. | — |
| **نشست مدیر** | فازها را برنامه‌ریزی می‌کند، taskها را تعریف می‌کند و prompt هر کدام را می‌نویسد. گزارش‌ها را با خود مخزن بازبینی می‌کند، task اصلاحی می‌نویسد و تابلوی taskها را نگه می‌دارد. | کد محصول نمی‌نویسد. شاخه پوشه اصلی را عوض نمی‌کند. چیزی را بدون تأیید مالک محصول ادغام یا مستقر نمی‌کند. |
| **نشست مجری** | دقیقاً یک task را انجام می‌دهد و با یک گزارش پایانی تمام می‌کند. | کار task دیگری را انجام نمی‌دهد. به فایل‌های مشترکی که در task نیامده دست نمی‌زند. |

## نام task و نام نشست

- **قالب نام:** `<شناسه> <عنوان کوتاه>`، مثل `M4-A1 cloud-db-fix`. شناسه یکتاست و تغییر نمی‌کند.
- **یکی بودن نام‌ها:** نام نشست مجری دقیقاً همان نام task است. این‌طوری در نوار نشست‌ها پیداست کدام task در حال اجراست.
  - خط اول هر prompt مجری خود نام task است. عنوانی که Claude Code خودکار می‌سازد معمولاً از همین خط می‌آید.
  - اگر عنوان فرق کرد، مالک محصول نشست را دستی تغییر نام می‌دهد:
    - **در VS Code:** در **Session history**، روی نشست hover کنید و **Rename** را بزنید.
    - **در CLI:** با `/rename <نام>`، یا از ابتدا با `claude -n "<نام>"`.
  - خود Claude نمی‌تواند نام نشست را عوض کند.
- **task اصلاحی:** به **همان نشست** داده می‌شود، تا زمینه کار حفظ شود و نام تغییر نکند. شناسه‌اش پسوند می‌گیرد، مثل `M4-A1.1`.

## جداسازی کار

- **هر task موازی worktree و شاخه خودش را دارد:**
  - worktree بیرون از پوشه مخزن ساخته می‌شود:
    ```
    git worktree add "D:/Claude Projects/recalino-wt/<شناسه>" -b <نوع>/<شناسه> <مبنا>
    ```
  - مالک محصول همان پوشه را در یک پنجره تازه VS Code باز می‌کند و نشست را آنجا شروع می‌کند.
  - در worktree تازه، `pnpm install` اجرا و `apps/web/.env.local` از پوشه اصلی کپی می‌شود. این فایل در git نیست.
- **پوشه اصلی** (`D:\Claude Projects\Recalino`) خانه همان taskی است که مدیر به آن سپرده است. در M4 این task، کار ادامه‌دار M4 روی شاخه `feat/plt-queue-storage` است.
- **منابع مشترک:** در هر لحظه فقط یک task از هر کدام استفاده می‌کند. مدیر این را در prompt می‌نویسد.

  | منبع | چرا مشترک است |
  |---|---|
  | Supabase محلی (Docker) | `db:reset`، migration و `db:types` داده و ساختار همه را عوض می‌کنند |
  | پورت 3000 | پیش‌فرض `pnpm dev` و آزمون E2E |
  | پروژه Vercel و دیتابیس ابری | deploy، متغیرهای محیطی و هر نوشتن |

  - **آزمون E2E روی پورت جدا:** `pnpm test:e2e` پورت را از `RECALINO_E2E_PORT` می‌گیرد (پیش‌فرض 3000). پس هر task می‌تواند E2E را روی پورت و Supabase ایزوله خودش اجرا کند.
  - **سروری که از قبل روی پورت است:** آزمون فقط وقتی از آن استفاده می‌کند که `next dev` همین checkout باشد (طبق `apps/web/.next/dev/lock`) و `apps/web/.env.local` بعد از شروعش تغییر نکرده باشد. وگرنه پیش از هر آزمون با پیام روشن متوقف می‌شود. سرور checkout دیگر را متوقف نکن؛ پورت آزاد دیگری بگیر.
  - **اجرای ایزوله:** وقتی `LOCAL_TEST_*` تنظیم شده، آزمون همیشه سرور خودش را بالا می‌آورد. Next.js در هر checkout فقط یک `next dev` اجرا می‌کند، پس `pnpm dev` همان checkout را پیش از آزمون ببند.

- **فایل‌های پرتعارض:** در هر فاز فقط یک task صاحب این‌ها است:
  - `CLAUDE.md`
  - `docs/TRACEABILITY_MATRIX.md`
  - `docs/MVP_FUNCTIONAL_REQUIREMENTS_FA.md`
  - `docs/PROJECT_SPEC.md`
  - `supabase/migrations/` و `packages/core/src/db/types.ts`
  - `pnpm-lock.yaml`
  - `apps/web/src/server/routes.ts`
  - `apps/web/src/ui/strings.ts`

  taskهای دیگر تغییر لازمشان را در گزارش می‌نویسند و مدیر آن را به task صاحب فایل می‌سپارد.

## چرخه کار

1. **مدیر** فاز را برنامه‌ریزی می‌کند: کدام taskها موازی، کدام پشت سر هم، و هر task کدام منبع مشترک را دارد. بعد prompt هر task را می‌نویسد.
2. **مالک محصول** برای هر task یک نشست باز می‌کند، prompt را می‌گذارد و نام نشست را با نام task یکی می‌کند.
3. **مجری:**
   - CLAUDE.md و اسناد نام‌برده را می‌خواند.
   - task را انجام می‌دهد و بررسی‌ها را اجرا می‌کند.
   - روی شاخه خودش commit می‌کند.
   - push یا باز کردن PR را فقط وقتی انجام می‌دهد که task گفته باشد.
   - با **گزارش پایانی** تمام می‌کند.
4. **مالک محصول** گزارش را به نشست مدیر می‌دهد.
5. **مدیر** گزارش را با خود مخزن بررسی می‌کند: `git log`، `git diff` و نتیجه CI. بعد یکی از این دو را تصمیم می‌گیرد:
   - **پذیرش:** task در تابلو «تمام» می‌شود.
   - **task اصلاحی:** برای همان نشست نوشته می‌شود.
6. **مدیر** تابلو را به‌روز می‌کند و prompt taskهای فاز بعد را می‌نویسد.

ادغام PR کد در `main`، استقرار، تغییر تنظیمات Vercel یا Supabase ابری و افزودن بسته همچنان پیش از انجام از مالک محصول پرسیده می‌شوند. نوشتن داده در دیتابیس ابری و `db push` برای migrationهای ادغام‌شده در `main` بدون پرسیدن انجام می‌شوند، جز کار غیرقابل‌برگشت روی داده (CLAUDE.md، بخش Supabase MCP؛ تصمیم مالک محصول 2026-10-10).

اول بخوان: CLAUDE.md، <اسناد مرتبط>

هدف: ...
دامنه: ... | بیرون از دامنه: ...
گام‌ها: ...
معیار پذیرش: ...
بررسی: <دستورها>
منابع مشترکی که این task مجاز است به کار ببرد: ...

مدیر کلمه ultracode را فقط برای taskهایی که کار چندعاملی نتیجه‌شان را آشکارا بهتر می‌کند، در خط آخر prompt می‌گذارد. این حالت پرهزینه و کند است (تصمیم مالک محصول، 2026-10-02).

## قالب گزارش پایانی مجری

مجری کار را با همین قالب و در **یک بلوک کد** تمام می‌کند تا مالک محصول بتواند آن را یک‌جا کپی کند. گزارش هیچ سری، کلید یا نشانی ایمیل پایلوت ندارد.

```text
## گزارش پایان task: <نام task>

- وضعیت: انجام شد | بخشی | متوقف (با دلیل)
- محل کار و شاخه: <پوشه/worktree> · <شاخه> · آخرین commit: <hash کوتاه و عنوان>
- push و PR: <ندارد | شاخه push شد | PR #n، وضعیت CI>
- کارهای انجام‌شده: ...
- فایل‌های تغییرکرده: <فهرست کوتاه>
- بررسی‌ها: <دستور ← نتیجه>، برای هر بررسی
- معیارهای پذیرش: ✅ یا ❌ برای هر معیار، با شاهد
- تفاوت با task و دلیل: ...
- مشکل‌ها و ریسک‌های باز: ...
- تصمیم یا اقدام لازم از مالک محصول: ...
- تغییرهای لازم در فایل‌های مشترک (برای مدیر): ...
- پیشنهاد گام بعد: ...
```

## تابلوی taskها

مدیر تابلو را در نشست خودش نگه می‌دارد و در شروع هر فاز آن را نشان می‌دهد. برای هر task این‌ها را ثبت می‌کند:

- شناسه و نام
- وضعیت: آماده، در حال اجرا، منتظر مالک محصول، تمام
- محل کار و شاخه
- منابع مشترک
- وابستگی‌ها

تابلو فایلی در مخزن نیست، تا تغییرهای پی‌درپی با شاخه‌های دیگر تعارض نسازند.
