## هدف و مرز

PLT زیرساخت مشترک و امنی است که همه ماژول‌های دیگر روی آن ساخته می‌شوند: نشست، کنترل مالکیت، قالب خطا، idempotency، صف کار پایدار، کنترل نرخ، لاگ بدون محتوای حساس، لینک امضاشده، نگهداری اسرار، پوسته PWA، متن دوجهته، دسترس‌پذیری و زمان.

**خارج از PLT:**

- ثبت‌نام، ورود و پروفایل ← `ACC`
- حذف داده ← `PRIV`
- دسترسی استثنایی پشتیبانی ← `OPS`
- بررسی سازگاری ضبط پیش از اولین ضبط ← `REC`

این FRها مستقل از Stack نوشته شده‌اند (فرض A8). هر جا فناوری نام برده شده، فقط مثالی از ADR-0001 است.

### FR-PLT-001 — نشست و مسیرهای محافظت‌شده

- **ارجاع:** PRD-SEC-01، PRD-REC-02، PRD-REC-03، NFR-01
- **مبنا:** قطعی (PRD-SEC-01)
- **اولویت:** P0
- **مرحله تحویل:** ۱
- **نقش مجاز:** learner. صفحه‌های عمومی (ورود، ثبت‌نام، شرایط استفاده، اطلاعیه حریم خصوصی) نقش لازم ندارند.
- **پیش‌شرط:** —
- **جریان اصلی:**
  1. هر درخواست به صفحه یا API غیرعمومی، نشست معتبر را سمت سرور بررسی می‌کند.
  2. بدون نشست معتبر:
     - صفحه به ورود هدایت می‌شود و مسیر بازگشت حفظ می‌شود.
     - API خطای `unauthenticated` برمی‌گرداند (FR-PLT-003).
  3. مسیر بازگشت فقط اگر مسیر نسبی داخل همین اپ باشد پذیرفته می‌شود.
  4. خروج، نشست را سمت سرور باطل می‌کند.
- **حالت‌های خالی / بارگذاری / خطا:**
  - اگر نشست حین ضبط منقضی شود، ضبط و ذخیره محلی بدون وقفه ادامه می‌یابند. فقط آپلود و درخواست‌های سرور تا ورود دوباره متوقف می‌مانند و وضعیت واقعی آن‌ها نمایش داده می‌شود (PRD-REC-02، PRD-REC-03).
  - پس از ورود دوباره، کار متوقف‌شده از همان نقطه ادامه می‌یابد.
- **ورودی و اعتبارسنجی:** توکن نشست در دسترس اسکریپت صفحه قرار نمی‌گیرد و فقط از کانال امن منتقل می‌شود.
- **تغییر وضعیت:** خروج ← نشست باطل.
- **خروجی:** —
- **مجوز دسترسی:** همه مسیرها به‌جز صفحه‌های عمومی، محافظت‌شده‌اند.
- **مصرف / سهمیه:** ندارد.
- **Idempotency:** خروج تکراری بی‌اثر است.
- **معیار پذیرش:**
  - Given درخواستی بدون نشست، When یک API محافظت‌شده فراخوانی شود، Then پاسخ `unauthenticated` با پاکت استاندارد است و هیچ داده‌ای برنمی‌گردد.
  - Given ضبطی در حال اجرا، When نشست منقضی شود، Then ضبط و ذخیره محلی ادامه می‌یابند، آپلود با وضعیت روشن متوقف می‌ماند و پس از ورود دوباره از همان نقطه ادامه می‌یابد.
  - Given مسیر بازگشتی به دامنه خارجی، When ورود کامل شود، Then کاربر به صفحه اصلی اپ هدایت می‌شود، نه به آن دامنه.
  - Given نشستی که خارج شده است، When توکن قبلی دوباره استفاده شود، Then رد می‌شود.

### FR-PLT-002 — کنترل مالکیت سمت سرور در هر خواندن و نوشتن

- **ارجاع:** PRD-SEC-01، PRD-SEC-04 (IDOR)، NFR-01
- **مبنا:** قطعی
- **اولویت:** P0
- **مرحله تحویل:** ۱
- **نقش مجاز:** learner، system
- **پیش‌شرط:** FR-PLT-001
- **جریان اصلی:**
  1. هر منبع داده یک مالک دارد، مستقیم یا از طریق منبع والد.
  2. هر خواندن، فهرست، نوشتن و حذف، مالکیت را در لایه دامنه سمت سرور و **پیش از هر اثر جانبی** بررسی می‌کند.
  3. فهرست‌ها فقط منابع همان کاربر را برمی‌گردانند.
  4. Job سیستمی فقط روی منابع مالکِ همان Job عمل می‌کند.
  5. دسترسی مستقیم به جدول‌ها با اعتبار کاربر نهایی، به‌عنوان لایه دفاعی دوم، رد می‌شود (ADR-0001، قاعده ۱).
- **حالت‌های خالی / بارگذاری / خطا:** منبع کاربر دیگر همان پاسخ `not_found` منبع ناموجود را می‌گیرد، تا وجود منبع افشا نشود.
- **ورودی و اعتبارسنجی:** شناسه‌ها غیرقابل حدس‌اند، اما دانستن شناسه، لینک یا شناسه Job مجوز نیست.
- **تغییر وضعیت:** —
- **خروجی:** —
- **مجوز دسترسی:** نقش `operator` فقط از مسیر FRهای ماژول OPS (مرحله ۵) دسترسی دارد.
- **مصرف / سهمیه:** ندارد.
- **Idempotency:** —
- **معیار پذیرش:**
  - Given کاربران A و B، When کاربر A هر منبع B را با شناسه‌اش بخواند، فهرست کند، ویرایش یا حذف کند، Then پاسخ `not_found` است و هیچ تغییری رخ نمی‌دهد.
  - Given آزمون خودکاری که همه مسیرهای ثبت‌شده API را فهرست می‌کند، When مسیری آزمون دسترسی بین‌حسابی نداشته باشد، Then آزمون شکست می‌خورد (NFR-01).
  - Given Jobی دست‌کاری‌شده که به منبع کاربر دیگری اشاره می‌کند، When اجرا شود، Then بدون اثر رد می‌شود و رخداد امنیتی ثبت می‌شود.
  - Given اعتبار کاربر نهایی، When مستقیم از جدول‌ها خوانده شود، Then دسترسی رد می‌شود.

### FR-PLT-003 — قالب یکسان خطای API

- **ارجاع:** PRD بخش ۳۱.۲ (قرارداد API با نمونه خطا)، PRD-PRIV-06
- **مبنا:** الزام بسته اجرایی PRD بخش ۳۱.۲
- **اولویت:** P0
- **مرحله تحویل:** ۱
- **نقش مجاز:** همه
- **پیش‌شرط:** —
- **جریان اصلی:**
  1. هر خطای API یک پاکت ثابت دارد:
     - `code`: پایدار و ماشینی
     - `message`: قابل نمایش به کاربر
     - `details`: اختیاری، مثلاً خطای هر فیلد
     - `request_id`
  2. نگاشت `code` به وضعیت HTTP ثابت است و در API_CONTRACTS ثبت می‌شود.
  3. کدهای پایه: `unauthenticated`، `not_found`، `validation_failed`، `conflict`، `idempotency_mismatch`، `rate_limited`، `quota_insufficient`، `payload_too_large`، `unsupported_media`، `internal`.
- **حالت‌های خالی / بارگذاری / خطا:** در پیام خطا هیچ‌یک از این موارد نمی‌آید: stack trace، SQL، مسیر داخلی، URL امضاشده و محتوای کلاس.
- **ورودی و اعتبارسنجی:** —
- **تغییر وضعیت:** —
- **خروجی:** پاکت خطا.
- **مجوز دسترسی:** —
- **مصرف / سهمیه:** —
- **Idempotency:** —
- **معیار پذیرش:**
  - Given ورودی نامعتبر، When درخواست ارسال شود، Then پاسخ `validation_failed` با خطای هر فیلد در `details` است.
  - Given خطای پیش‌بینی‌نشده، When رخ دهد، Then پاسخ `internal` فقط `request_id` دارد و جزئیات فقط در لاگ پاک‌سازی‌شده ثبت می‌شود (FR-PLT-007).
  - Given آزمون قرارداد، When هر پاسخ خطای API بررسی شود، Then با Schema پاکت منطبق است.

### FR-PLT-004 — Idempotency درخواست‌های تغییردهنده

- **ارجاع:** PRD-PROC-03، NFR-02، AC-13
- **مبنا:** قطعی (PRD-PROC-03)
- **اولویت:** P0
- **مرحله تحویل:** ۱
- **نقش مجاز:** learner، system
- **پیش‌شرط:** FR-PLT-001
- **جریان اصلی:**
  1. درخواست‌های سه دسته کلید idempotency **الزامی** دارند: ساخت منبع، مصرف یا رزرو سهمیه، و آغاز کار AI. کلید را کلاینت می‌سازد.
  2. سرور کلید را همراه کاربر، مسیر و hash بدنه ثبت می‌کند و برای ارسال‌های بعدی، پاسخ نخست را برمی‌گرداند.
  3. مدت نگهداری کلید قابل پیکربندی است (مصوب برای پایلوت: ۲۴ ساعت).
  4. رخداد مرور با `review_event_id` خودش (PRD-SRS-10) از همین سازوکار پیروی می‌کند.
- **حالت‌های خالی / بارگذاری / خطا:**
  - اگر دو درخواست هم‌زمان همان کلید را داشته باشند، فقط یکی اجرا می‌شود. دیگری یا `conflict` (در حال اجرا) می‌گیرد، یا پس از اتمام همان نتیجه را.
  - همان کلید با بدنه متفاوت ← `idempotency_mismatch`.
- **ورودی و اعتبارسنجی:** درخواست بدون کلید در دسته‌های الزامی ← `validation_failed`.
- **تغییر وضعیت:** ثبت کلید و پاسخ.
- **خروجی:** پاسخ نخست.
- **مجوز دسترسی:** کلید در محدوده همان کاربر معتبر است.
- **مصرف / سهمیه:** ارسال تکراری سهمیه دوم کم نمی‌کند (PRD-COST-02).
- **Idempotency:** موضوع همین FR است.
- **معیار پذیرش:**
  - Given درخواست ایجاد با کلید K، When دو بار ارسال شود، Then یک منبع ساخته می‌شود و هر دو پاسخ یکسان‌اند.
  - Given همان کلید K با بدنه متفاوت، When ارسال شود، Then پاسخ `idempotency_mismatch` است و اثری ندارد.
  - Given دو درخواست هم‌زمان با کلید K، When پردازش شوند، Then دقیقاً یک اثر ثبت می‌شود.
  - Given مسیری از دسته الزامی، When بدون کلید فراخوانی شود، Then پاسخ `validation_failed` است.

### FR-PLT-005 — صف کار پایدار

- **ارجاع:** PRD-ARCH-02، PRD-PROC-01، PRD-PROC-03، NFR-02
- **مبنا:** قطعی (PRD-ARCH-02)؛ پیاده‌سازی طبق ADR-0001
- **اولویت:** P0
- **مرحله تحویل:** ۱
- **نقش مجاز:** system
- **پیش‌شرط:** —
- **جریان اصلی:**
  1. Job در **همان تراکنشی** ثبت می‌شود که تغییر دامنه مربوط را ذخیره می‌کند. اگر تراکنش برگشت بخورد، Job وجود ندارد.
  2. Payload فقط شناسه و نسخه است، نه محتوای کلاس.
  3. اجرا بلافاصله پس از ثبت آغاز می‌شود. یک محرک دوره‌ای هم Jobهای جامانده و Retryها را برمی‌دارد.
  4. هر Job سقف تلاش و فاصله رو به افزایش دارد (قابل پیکربندی). پس از آخرین تلاش، وضعیت `failed` با علت قابل بررسی می‌گیرد.
  5. Jobی که مهلت اجرایش بگذرد (crash یا timeout)، دوباره قابل برداشت می‌شود.
  6. Handlerها idempotent‌اند: اثر هر مرحله با کلید مرحله ثبت می‌شود و اجرای دوباره اثر دوم ندارد.
  7. Job لغوشده اجرا نمی‌شود، و Handler در مرز هر مرحله وضعیت لغو را بررسی می‌کند.
- **حالت‌های خالی / بارگذاری / خطا:** وضعیت‌های Job: `queued`، `running`، `retry_scheduled`، `succeeded`، `failed`، `cancelled`.
- **ورودی و اعتبارسنجی:** Payload با Schema نسخه‌دار اعتبارسنجی می‌شود.
- **تغییر وضعیت:** طبق فهرست بالا.
- **خروجی:** —
- **مجوز دسترسی:** فقط system. کاربر وضعیت کار را از ماژول مالک آن می‌بیند، مثلاً PROC.
- **مصرف / سهمیه:** Retry خطای سیستم سهمیه کاربر را دوباره کم نمی‌کند (PRD-COST-02).
- **Idempotency:** بند ۶.
- **معیار پذیرش** (همه روی Postgres واقعی و deterministic اجرا می‌شوند، نه mock):
  - Given تراکنشی که Run و Job را می‌سازد، When برگشت بخورد، Then هیچ Jobی وجود ندارد.
  - Given crash اجراکننده وسط یک مرحله، When مهلت Job بگذرد، Then Job دوباره اجرا می‌شود و اثر آن مرحله دقیقاً یک بار وجود دارد.
  - Given تحویل هم‌زمان یک Job به دو اجراکننده، When هر دو شروع کنند، Then فقط یکی مرحله را اجرا می‌کند.
  - Given Jobی که همیشه شکست می‌خورد، When به سقف تلاش برسد، Then وضعیت `failed` با علت ثبت می‌شود و تلاش بی‌پایان رخ نمی‌دهد.
  - Given Jobی لغوشده، When نوبت اجرایش برسد، Then اجرا نمی‌شود.

### FR-PLT-006 — کنترل نرخ

- **ارجاع:** PRD-SEC-04، PRD-COST-06
- **مبنا:** قطعی (PRD-SEC-04)
- **اولویت:** P1
- **مرحله تحویل:** ۱
- **نقش مجاز:** learner و درخواست‌های عمومی
- **پیش‌شرط:** —
- **جریان اصلی:**
  1. محدودیت برای هر کاربر و هر IP روی این مسیرها اعمال می‌شود: ورود، ثبت‌نام و بازیابی؛ صدور URL آپلود؛ درخواست‌های آغازکننده AI؛ ساخت خروجی.
  2. مقادیر در پیکربندی‌اند، نه در کد.
- **حالت‌های خالی / بارگذاری / خطا:** عبور از محدودیت ← `rate_limited` همراه با `Retry-After`.
- **ورودی و اعتبارسنجی:** —
- **تغییر وضعیت:** شمارنده‌های پنجره زمانی.
- **خروجی:** —
- **مجوز دسترسی:** —
- **مصرف / سهمیه:** کنترل نرخ با سهمیه (QUOTA) فرق دارد و جایگزین آن نیست.
- **Idempotency:** —
- **معیار پذیرش:**
  - Given محدودیت N درخواست در پنجره، When درخواست N+1 برسد، Then پاسخ `rate_limited` با `Retry-After` است.
  - Given عبور مکرر از محدودیت، When تکرار شود، Then رخداد امنیتی ثبت می‌شود (FR-PLT-007).

### FR-PLT-007 — لاگ فنی و رخداد امنیتی بدون محتوای حساس

- **ارجاع:** PRD-PRIV-06، PRD-SEC-04، PRD بخش ۴.۱ (عملیات)
- **مبنا:** قطعی
- **اولویت:** P0
- **مرحله تحویل:** ۱
- **نقش مجاز:** system
- **پیش‌شرط:** —
- **جریان اصلی:**
  1. لاگ ساخت‌یافته این فیلدها را دارد: `request_id`، شناسه کاربر، مسیر، وضعیت و مدت.
  2. پیش از نوشتن هر لاگ یا رخداد تحلیلی، لایه پاک‌سازی اعمال می‌شود.
  3. این موارد هرگز ثبت نمی‌شوند:
     - متن transcript، جزوه یا کارت
     - محتوای فایل
     - Prompt یا خروجی مدل که محتوای کلاس دارد
     - رمز، توکن نشست، کلید API و URL امضاشده
  4. این رخدادهای امنیتی جدا ثبت می‌شوند: شکست پیاپی ورود، رد مالکیت، عبور از نرخ، Job دست‌کاری‌شده.
  5. AuditEvent حداقلی برای عملیات حساس (حذف، دسترسی استثنایی) جدا نگهداری می‌شود.
- **حالت‌های خالی / بارگذاری / خطا:** اگر لایه پاک‌سازی شکست بخورد، لاگ آن رکورد با پیام عمومی جایگزین می‌شود، نه با متن خام.
- **ورودی و اعتبارسنجی:** —
- **تغییر وضعیت:** —
- **خروجی:** —
- **مجوز دسترسی:** لاگ‌ها فقط برای نقش‌های عملیاتی قابل دسترسی‌اند.
- **مصرف / سهمیه:** —

### FR-PLT-014 — لایه واسط ذخیره‌سازی و تطبیق دوره‌ای

- **ارجاع:** ADR-0001 (قاعده ۲ و ۹)، PRD-SEC-01، PRD-DATA-05، PRD-DEL-03، D29
- **مبنا:** قطعی (ADR-0001، قاعده ۹)؛ عملیات یکپارچه‌سازی قطعه‌ها وابسته به SPIKE-05 (Q-SRC-4)
- **اولویت:** P0
- **مرحله تحویل:** ۱
- **نقش مجاز:** system
- **پیش‌شرط:** —
- **جریان اصلی:**
  1. همه کار با فایل از یک رابط نازک عبور می‌کند؛ کد دامنه هیچ‌جا SDK تأمین‌کننده ذخیره‌سازی را مستقیم صدا نمی‌زند. عملیات رابط:
     - صدور لینک امضاشده نوشتن و خواندن (FR-PLT-008)
     - بررسی وجود، حجم و checksum یک شیء
     - حذف
     - فهرست بر اساس پیشوند
     - یکپارچه‌سازی قطعه‌ها به یک شیء خواندنی؛ روش در SPIKE-05 تعیین می‌شود (Q-SRC-4)
  2. **دو پیاده‌سازی:** Vercel Blob برای محیط ابری، و پیاده‌سازی درون‌حافظه یا دیسک محلی برای آزمون و توسعه، تا آزمون بدون اینترنت و بدون مصرف اعتبار اجرا شود.
  3. **رکورد شیء:** هر شیء با کلید مستقل از تأمین‌کننده، ماژول مالک، کلاس نگهداری و وضعیت در Postgres ثبت می‌شود. URL تأمین‌کننده هرگز ذخیره نمی‌شود.

  6. حذف داده (PRD-DEL-03) فقط از همین لایه انجام می‌شود تا شیئی جا نماند.
- **حالت‌های خالی / بارگذاری / خطا:** خطای موقت تأمین‌کننده ← Retry طبق FR-PLT-005؛ خطای نهایی ← رخداد عملیاتی.
- **ورودی و اعتبارسنجی:** کلید شیء را فقط سرور می‌سازد؛ ورودی کاربر هرگز بخشی از مسیر ذخیره نیست.
- **تغییر وضعیت:** رکورد شیء: «در انتظار» ← «تأییدشده» ← «حذف‌شده».
- **خروجی:** —
- **مجوز دسترسی:** فقط system؛ ماژول‌ها از API عمومی این لایه استفاده می‌کنند.
- **مصرف / سهمیه:** ندارد؛ ظرفیت با QUOTA است (FR-QUOTA-011).
- **Idempotency:** حذف دوباره یک شیء بی‌اثر است. ثبت دوباره رکورد با همان کلید، رکورد دوم نمی‌سازد.
- **معیار پذیرش:**
  - Given آزمون مرز ماژول‌ها، When کد دامنه بررسی شود، Then هیچ import مستقیمی از SDK تأمین‌کننده ذخیره‌سازی بیرون از پیاده‌سازی این لایه وجود ندارد.
  - Given مجموعه آزمون، When با پیاده‌سازی درون‌حافظه اجرا شود، Then هیچ درخواست شبکه‌ای به تأمین‌کننده ذخیره‌سازی ارسال نمی‌شود.
  - Given رکورد «تأییدشده» بدون شیء، When Job تطبیق اجرا شود، Then رخداد عملیاتی ثبت می‌شود و رکورد حذف نمی‌شود.
  - Given شیء بی‌رکورد جوان‌تر از مهلت، When Job تطبیق اجرا شود، Then حذف نمی‌شود.
  - Given هر رکورد شیء، When بررسی شود، Then URL تأمین‌کننده در پایگاه داده نیست.
